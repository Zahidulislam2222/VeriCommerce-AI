# Threat model

Scope: browser, public reverse proxy, API, PostgreSQL, worker, model cache, accounts, uploads, read-only Shopify, content review, approval/export and release artifacts. Current release `20261018-phase5-02` follows quota release `20261018-phase3-01`, the integrated expansion `20261018-phase1-01` and the verified 2026-10-15 evidence release, with 228 matching artifacts and four verified healthy services. The final clean production-locked backend/infrastructure suite passed 142 checks, including direct-pin/hash-lock consistency; 46 live browser checks belong to the preceding expansion, with current store flows verified separately. This is a design review, not a penetration-test certificate or a claim that every external acceptance gate passed.

Trust boundaries are crossed at the public request, cookie-to-membership mapping, database connection, worker claim, disposable parser IPC, model artifact download, Shopify transport/webhook and release promotion. A source citation establishes lineage, not truth; malicious or incorrect source documents can still produce incorrect evidence-backed quotations. Source deletion and store-data retirement exclude current evidence but do not promise erasure of retained revisions/citations or backups.

Prompt injection is limited today because retrieved text does not execute tools. Future generative workflows must authorize tool arguments and publishing in application code, restrict egress and test hostile documents/images/tool results. Do not rely on an instruction asking a model to ignore malicious text. [OWASP prompt injection](https://genai.owasp.org/llmrisk/llm01-prompt-injection/).

Session controls follow standard cookie guidance but require actual configuration and browser checks. HttpOnly reduces script access to tokens; it does not remove XSS impact. [OWASP session management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).

The deployed application implements roles, account sessions and integration-token encryption, but their existence is not a complete merchant-service security program. Automated recovery/email verification, operational key rotation, retention/deletion requests, processor agreements, abuse monitoring, incident notification and independently reviewed accessibility/upload behavior require explicit operational acceptance. Shopify publishing and public-app distribution are later boundaries; applicable privacy-webhook and distribution requirements cannot be inferred from this catalog-only connector.

## Security gates as the service grows

Preserve authorization in every protected API and worker effect as replicas, caches and regional cells are introduced. A tenant or role supplied by a browser is an expected-scope fence, not proof of membership. Reset transaction-local context on pooled connections, recheck privileges around writes and invalidate cached access after membership changes. Test cross-tenant cache keys, job claims, object paths, exports and support tooling as well as ordinary SQL reads. [OWASP multi-tenant guidance](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html).

Prioritize operational administrator MFA, tested key rotation/recovery, scoped support access, dependency/model monitoring, rate/bot admission and bounded security telemetry before expanding the data population. Protect auth, upload/parser, callback/webhook and recovery entry points against bypass and abuse. An external WAF or provider plan must be evaluated for actual route coverage and cost; it cannot replace application authorization. For future publishing, server-owned permissions, remote state reconciliation and audit must surround each approved action, including unknown timeout outcomes.

The [capacity plan](SCALABILITY-AND-COST.md) treats overload as an availability risk and [data governance](PRIVACY-AND-LEGAL.md) tracks retention, regional placement and applicable US/EU requirements. Expansion gates include isolation/correctness under failure, not only throughput or a provider's certification.
